## 아키텍처와 학습 목표

이 프로젝트는 클린 아키텍처를 처음 적용해 보는 실습이다. 의존성이 안쪽으로 향하도록 설계하고, 그 결과 유스케이스를 Spring, 데이터베이스, 외부 HTTP 서비스 없이 실행하고 테스트할 수 있는 이유를 이해하는 것이 목표다.

`POST /api/products`는 `name`, `price`, `imageUrl`을 JSON으로 받는다. 상품 등록 유스케이스는 상품을 검증한 뒤 PurgoMalum으로 상품명을 검사하고, 통과한 상품을 저장한다. Spring MVC 컨트롤러는 `@Service`로 등록한 유스케이스를 호출한다. Spring Data JPA 저장소와 PurgoMalum HTTP 클라이언트는 각각 유스케이스가 정의한 인터페이스를 구현한다.

가격은 0보다 커야 하고, 이미지 URL은 호스트가 있는 HTTP 또는 HTTPS 주소여야 한다. 성공하면 `201 Created`와 생성된 상품을 반환한다. 입력이 잘못됐거나 비속어가 확인되면 `400 Bad Request`, 비속어 검사를 완료할 수 없으면 `503 Service Unavailable`과 오류 메시지를 JSON으로 반환한다.

회원 비밀번호는 해시로 저장하고, 회원 가입과 로그인에는 같은 토큰 발급 방식을 사용한다. 위시 리스트 조회와 변경은 토큰으로 식별한 회원의 항목에 한정한다. 저장 방식의 세부 사항, 토큰 형식과 만료 시간, 위시 리스트 중복 추가, 상품 삭제 시 위시 리스트 처리 정책은 각 기능을 설계할 때 논의한다.

로컬 데이터베이스는 SQLite를 사용한다. 앱을 실행한 디렉터리에 `shopping.db`가 생성되며, Hibernate의 `ddl-auto=update` 설정으로 로컬 테이블을 생성한다. 상품명 15자 제한은 애플리케이션에서 적용한다.

## 기능 구현 순서

기능마다 다음 순서를 반복한다.

1. 기능의 동작과 성공·실패 시나리오를 정의한다.
2. 클린 아키텍처에서 기능의 경계와 의존성 방향을 정한다.
3. 기능에 필요한 도메인 객체와 각 객체의 책임, 객체 간 관계를 정한다.
4. JUnit과 AssertJ로 첫 번째 동작을 검증하는 테스트를 작성한다.
5. 테스트를 통과하도록 구현한다. 남은 시나리오도 테스트 작성과 구현을 반복하고, 기능 단위로 커밋한다.

애플리케이션과 테스트 코드는 학습자가 직접 작성한다. AI는 [AGENTS.md](AGENTS.md)에 따라 설계 논의, 개념 설명, 테스트 시나리오 검토, 코드 리뷰를 돕는다.

## AI 활용 기록

- Codex로 프리코스 가이드 두 개를 읽고, 기능 목록과 구현 전략 초안을 작성했다. 논의에서 정한 아키텍처와 기능 구현 순서도 문서에 정리했다. 이후 AI를 어떻게 활용했는지, 직접 수정한 코드와 배운 점은 작업하면서 기록한다.
- 로컬 데이터베이스를 SQLite로 설정하고 Flyway 의존성을 제거했다. 상품명 자체의 규칙과 외부 비속어 검사의 책임을 어디에 둘지 논의했다.
- 학습자가 `ProductName` 레코드에 빈 이름, 공백 포함 15자 제한, 허용 문자 검사를 구현하고 JUnit과 AssertJ로 거절 사례를 작성했다. Codex와 생성자 예외를 검증하는 위치와 하나의 테스트를 여러 입력으로 실행하는 방법을 살펴봤다. 다음 구현은 PurgoMalum API 연동이다.
- 비속어 검사 인터페이스와 PurgoMalum HTTP 구현체를 작성하고, 검사 결과와 서비스 호출 실패를 구분했다.
- 상품 도메인, 등록 유스케이스, JPA 저장소, HTTP API를 연결했다. 로컬 모의 서버와 SQLite를 사용해 등록 성공 및 실패 흐름을 검증했다.
- 상품 등록 서비스는 `@Service`로 등록하고, 엔티티 변환과 저장을 Spring Data JPA 저장소에 모았다.
