# spring-shopping-precourse

Spring Boot로 상품, 회원, 위시리스트 API를 구현한다. 애플리케이션 API의 요청과 응답은 본문이 있는 경우 JSON으로 처리한다.

### 구현 순서를 정한 이유

- 회원 가입에서 계정과 토큰 발급을 만들고, 로그인에서 인증 정보 확인과 토큰 발급을 연결한다. 회원 인증 흐름을 먼저 준비하는 순서로 잡았다.
- 상품 등록 후 단건·목록 조회를 구현하여 저장한 상품을 확인할 수 있게 한다. 이어서 수정 기능에 등록 시 만든 검증을 재사용한다.
- 회원과 상품이 준비되면 위시리스트를 구현한다. 추가 기능에서 토큰 검증과 회원별 항목 저장을 연결하고, 조회와 삭제에서 이를 활용한다.
- 상품 삭제는 마지막에 구현한다. 위시리스트에 담긴 상품을 삭제했을 때의 처리까지 함께 결정하고 반영한다.

커밋 제목은 `<type>: <한글 변경 요약>` 형식으로 작성한다. `feat`, `fix`, `docs`, `test` 등 영어 프리픽스를 사용하고, 제목은 변경 내용을 설명하는 짧은 구절로 쓰며 끝에 마침표를 붙이지 않는다. 본문이 필요하면 빈 줄 뒤에 변경 이유를 한글로 적고 각 줄을 100자 이내로 작성한다. [Git Commit Message Conventions](https://gist.github.com/stephenparish/9941e89d80e2bc58a153)

## 현재 구현 범위와 보류 항목

- 미정인 정책은 결정 후 구현한다. 비밀번호 최소 길이, 토큰 생성 방식과 만료 시간, 가격 범위, 추가 이미지 URL 검증, 공백만 있는 상품 이름의 처리, 위시리스트 중복·수량 정책과 상품 삭제 시 위시리스트 처리가 이에 해당한다.
- 가입은 이메일 형식과 필수값을 검사하고 계정을 저장한다. 비밀번호는 Spring Security의 PBKDF2로 해시한다. 가입·로그인에서 토큰 발급은 보류한다. 이 단계의 응답은 `{"memberId": 1}`이다.
- 이메일은 로그인 식별자로 사용하며 DB 유일성 제약으로 중복 가입을 방지한다. 가입 성공은 201, 중복 이메일은 409로 응답한다.
- 기존 H2 의존성과 Flyway로 테이블을 생성하고 JPA 스키마를 검증한다. 기본 내장 H2는 메모리 DB이므로 실행을 종료하면 데이터가 사라진다.
- 테스트 케이스는 제안 단계다. 합의한 케이스가 생기면 JUnit·AssertJ 테스트를 추가한다.

## 구현 전략

### 회원과 인증

- 회원은 이메일과 비밀번호로 인증할 수 있는 계정과 자신의 위시리스트를 가진다. 가입 시 비밀번호 해시를 저장하고, 로그인 시 입력값을 저장된 해시와 비교한다.
- 이메일 주소는 기본적으로 `로컬 부분@도메인` 형태다. 프로젝트에 있는 Jakarta Validation의 `@NotBlank`와 `@Email`을 조합하는 방안을 제안한다. `@Email`의 세부 판정 기준은 구현체에 따라 달라지며, 주소 형식만 검사한다. [Jakarta Validation @Email](https://jakarta.ee/specifications/bean-validation/3.1/apidocs/jakarta/validation/constraints/Email.html)
- 비밀번호는 최소 길이를 검사한다. 이 과제의 최솟값은 아직 정하지 않았다. 이메일과 비밀번호로 로그인하는 흐름을 기준으로 15자를 초안으로 제안한다. NIST는 비밀번호를 단일 인증 요소로 쓸 때 최소 15자를 요구하며, 문자 종류 조합 규칙을 부과하지 않도록 한다. [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)
- 무작위 토큰과 서명된 JWT를 비교한다. 무작위 토큰은 서버에 저장한 값과의 일치 여부, 회원, 만료 시간을 확인해야 하며, 서버에서 기록을 무효화하기 쉽다. 서명된 JWT는 토큰에 포함된 정보와 서명, 만료 시간을 검증해 회원을 식별할 수 있으며, 만료 전 개별 토큰을 취소하려면 별도 상태가 필요하다. 이번 과제에는 `SecureRandom`으로 만든 무작위 문자열 토큰과 `Authorization: Bearer <token>`을 제안한다. 토큰 방식과 만료 기간은 가입 기능 구현 전에 정한다. [OWASP 세션 관리 가이드](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519)

### 상품

- 기존 Spring MVC, Jakarta Validation, Spring Data JPA 구성을 활용한다. 컨트롤러가 JSON을 받고 응답하고, 상품 저장과 조회는 저장소에 맡긴다.
- 이름은 공백을 포함해 1~15자여야 한다. 허용하는 특수문자는 `(`, `)`, `[`, `]`, `+`, `-`, `&`, `/`, `_`이다. 등록과 수정에서 같은 검증 로직을 쓴다.
- 길이와 허용 문자를 먼저 검사한다. 통과한 이름을 URL 인코딩하여 PurgoMalum의 `GET /service/containsprofanity?text=...`에 전달하고, 본문이 `true`이면 검증 오류로 처리한다. 연결 실패·시간 초과·예상 밖 응답은 검증 서비스 오류로 처리하여 저장을 중단하는 방안을 제안한다. [PurgoMalum API](https://www.purgomalum.com/)
- 상품 이름에서 공백만 있는 문자열을 허용할지, 이미지 URL과 가격의 세부 검증 기준을 어떻게 잡을지 등록 기능 구현 전에 정한다.

### 위시리스트

- 추가·삭제·조회에서 토큰을 공통으로 검증한 뒤, 확인된 회원의 항목만 다룬다. 상품 추가 전에 등록된 상품인지 확인한다.
- Java의 `List`는 순서가 있는 목록으로 일반적으로 중복을 허용한다. `Set`은 중복을 허용하지 않는다. `Map`은 상품 ID 같은 키에 수량 같은 값을 연결할 수 있다. 응답에 상품 목록을 담을 때는 `List`를 사용할 수 있다. [Java List](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/List.html), [Java Set](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Set.html), [Java Map](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Map.html)
- 사용자 요구사항의 조회·추가·삭제 흐름을 기준으로, 회원별 상품을 한 번만 저장하고 수량은 두지 않는 방안을 제안한다. 이 경우 DB에서 회원 ID와 상품 ID 쌍에 유일성 제약을 둘 수 있다. 수량을 도입한다면 재추가 시 증가량과 삭제 시 한 개 차감 또는 항목 전체 제거 중 어떤 동작을 할지 함께 정한다.
- 위시리스트 구현 전에 재추가 요청의 응답, 삭제할 상품 ID의 전달 방식, 위시리스트에 담긴 상품이 상품 API에서 삭제되는 경우의 처리를 정한다.

## 테스트 계획

JUnit과 AssertJ로 구현한 기능의 동작을 검증한다. 아래는 협의할 테스트 후보이며, 실제로 작성할 케이스는 사용자와 정한 뒤 추가한다.

| 대상 | 테스트 후보 |
| --- | --- |
| 상품 | 등록·조회·수정·삭제의 정상 흐름, 이름 1자·15자 경계와 0자·16자 실패, 허용 문자와 금지 문자, 비속어 검출 및 외부 API 오류 |
| 회원 | 가입·로그인 성공 시 토큰 발급, 이메일 형식 오류, 최소 길이 미달, 일치하지 않는 인증 정보 |
| 위시리스트 | 회원별 추가·조회·삭제, 유효한 토큰이 없는 요청 거절, 다른 회원의 항목 격리, 미등록 상품 추가와 미포함 상품 삭제 실패 |

비속어 검사 테스트는 외부 API 응답을 제어할 수 있게 구성하는 방안을 제안한다.

## 푸시 전 체크리스트

- [ ] [Google Java Style Guide](https://google.github.io/styleguide/javaguide.html)를 기준으로 Java 코드 컨벤션을 확인했다.
- [ ] 들여쓰기 한 단계는 공백 4칸이며, 제어문 중첩은 최대 두 단계다. 예를 들어 `while` 안의 `if`는 두 단계로 센다.
- [ ] 각 함수와 메서드는 15줄 이내이고 한 가지 일만 한다.
- [ ] `else`, `switch`, 삼항 연산자를 사용하지 않았다.
- [ ] 합의한 JUnit·AssertJ 테스트를 실행하고 결과를 확인했다.
- [ ] 기능 목록과 커밋 메시지, AI 활용 및 학습 기록을 확인했다.
