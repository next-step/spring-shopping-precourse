# spring-shopping-precourse

## 실행 방법

- Java 21이 필요하다. (`java -version`으로 확인)
- 서버 실행: `gradlew.bat bootRun`
- 테스트 실행: `gradlew.bat clean test`
- 데이터는 H2 인메모리 DB에 저장되므로 서버를 재시작하면 사라진다.

## 구현한 기능 목록

## 상태 코드

| 기능 | 성공 | 실패 |
|---|---|---|
| 상품 추가 | 201 | 400(입력 오류), 503(비속어 검사 불가) |
| 상품 조회·목록·수정 | 200 | 400(수정 시 입력 오류), 404(없는 상품) |
| 상품 삭제 | 204 | 404 |
| 회원 가입 | 201 | 400(형식 오류), 409(중복 이메일) |
| 로그인 | 200 | 400(형식 오류), 401(정보 불일치) |
| 위시 추가 | 201 | 400, 401, 404(없는 상품), 409(이미 담음) |
| 위시 조회 | 200 | 401 |
| 위시 삭제 | 204 | 401, 403(남의 위시), 404(없는 위시) |

오류 응답은 `{"message": "..."}` 형태로 통일한다.

## 구현 전략

- 기능 목록의 한 줄을 하나의 커밋 단위로 삼아, 구현 → 테스트 → 커밋 순서로 진행한다.
- Controller(요청 처리), Service(규칙 처리), Repository(저장)로 역할을 나눈다.
- H2(인메모리 DB)와 Spring Data JPA로 저장하고, 스키마는 Flyway SQL로 관리한다.
- 상품 이름 규칙은 추가와 수정이 함께 쓰도록 한 곳에서 검사한다.
- 비속어 검사는 인터페이스로 분리하고, 테스트에서는 가짜 구현으로 대체한다.
- 비속어 검사 서비스에 장애가 나면 검사하지 못한 이름을 통과시키지 않고 503으로 응답한다.
- 로그인 시 발급한 토큰을 요청 헤더로 받아, 위시 리스트 API에서 회원을 식별한다.
- 예외는 `GlobalExceptionHandler`에서 한곳에서 상태 코드로 변환해 응답한다.

## 패키지 구조

기능(도메인) 기준으로 나누고, 여러 기능이 함께 쓰는 것은 `auth`, `common`에 둔다.

```
shopping
├── member   회원 (controller, service, repository, domain, exception)
├── product  상품 (controller, service, repository, domain, exception, client)
├── wish     위시 리스트 (controller, service, repository, domain, exception)
├── auth     JWT 발급·검증, 비밀번호 인코더, @LoginMember 인자 해석기
└── common   전역 예외 처리, 오류 응답 형식
```

- 호출 방향은 `controller → service → repository` 한 방향으로만 한다.
- `product/client`에는 비속어 검사(PurgoMalum) 외부 API 연동을 둔다.
- `wish`는 `product`를 참조하고, 회원은 id로만 가진다.

## 인증(토큰) 전략

1. 로그인에 성공하면 서버가 토큰을 발급해 응답한다.
2. 클라이언트는 이후 요청의 `Authorization` 헤더에 `Bearer {토큰}` 형태로 토큰을 보낸다.
3. 인증이 필요한 API(`/api/wishes/**`)의 Controller 파라미터에 `@LoginMember`를 붙이면, 인자 해석기가 토큰을 검사해 회원 id를 채워 준다.
4. 토큰이 없거나 유효하지 않으면 401을 응답한다.
5. Controller는 식별된 회원 id를 전달받아 사용만 하고, 토큰을 직접 해석하지 않는다.

- 토큰 방식: JWT를 사용한다. 토큰에 회원 식별 정보를 담아 서버에 토큰을 따로 저장하지 않는다.
- 비밀번호는 평문이 아닌 BCrypt 해시로 저장하고, 로그인 시 입력값과 해시를 비교한다.
- 로그인 실패 시 이메일 오류와 비밀번호 오류를 구분하지 않고 같은 응답을 준다.
- 위시 삭제 시 해당 항목의 주인이 로그인한 회원인지 확인하고, 아니면 403을 응답한다.

## AI 도구 활용 기록

### 활용 방법
- 프로젝트 구조(Controller → Service → Repository)와 구현 순서를 AI와 함께 잡았다.
- 테스트 코드를 작성할 때, 바로 받지 않고 의사코드를 보고 직접 작성한 뒤 AI에게 검토를 받았다.
- 이해되지 않는 부분(JPA, Jwt 토큰, record, @WebMvcTest 를 비롯한 @ 문법들 등)은 질문해서 예시와 함께 설명을 들었다.

### 직접 판단하고 바꾼 점
- 테스트 → 구현 → 커밋 방향으로 개발하려 했으나, 시간이 오래걸려서 구현 → 테스트 → 커밋 방향으로 바꾸었다.
- PurgoMalum이 영어 비속어만 검사하므로 한국어 비속어는 걸러지지 않는 한계를 확인했다.
- 비속어 검사 서비스가 응답하지 않으면 등록을 거절(503)하기로 했다.
- 테스트가 통과해도 의미 없는 테스트일 수 있어서, 구현을 일부러 망가뜨려 테스트가 실패하는지 확인했다.
- 상품 이름이 공백뿐이면 무효로 본다. 
- 이미지 URL은 http:// 또는 https://로 시작해야 하고, 가격은 0 이상이다. 
- 상품이 삭제되면 그 상품을 담은 위시도 함께 삭제한다(오류로 막는 대신). 
- 비밀번호는 BCrypt 해시, JWT 비밀키는 설정 파일에 두었다(실서비스에서는 환경변수로 분리해야 한다는 한계).
- 인증(WebConfig)을 추가한 뒤 기존 컨트롤러 테스트 13개가 한꺼번에 실패했다. AI에게 원인을 확인받았고,
  @WebMvcTest는 웹 계층만 띄우는데 WebConfig가 JwtTokenProvider를 요구하지만 그 부품은 로드되지
  않아서라는 것을 이해했다. 테스트에 @MockitoBean으로 가짜 JwtTokenProvider를 추가해 해결했고,
  이후 만든 위시리스트 컨트롤러 테스트에도 같은 방식을 적용했다.

### 배운 점
- 테스트 → 구현 → 커밋 방향은 안정성은 있으나 속도가 느리고, 구현 → 테스트 → 커밋 방향은 안정성은 떨어지나 속도는 빠르다는 것을 직접 만들어보면서 느꼈다.
- Controller 는 요청과 응답을 하고, Service 는 규칙 판단을 하고, Repository는 저장만 하도록 나누니, 각각에 따라 테스트 방식이 바뀐다는 것을 알았다.
- 여러 기능이 다같이 쓰는 코드는 (전역 예외 처리, 오류 응답)는 common에, 인증 관련된 코드들은 auth 에 놓는 것을 보면서 폴더를 나누는 기준이 어떤지 알게 되었다.
- 스프링의 어노테이션(@Component, @Service, @Bean, @Configuration)과 JPA의 어노테이션(@Entity, @Id, @ManyToOne)이 각각 어떤 역할인지 구분해서 알게 되었다.
- 외부 API는 실패할 수 있으므로 실패했을 때의 정책을 정해야 한다.
- 비밀번호를 해시(BCrypt)로 저장하는 이유가, DB가 유출돼도 원래 비밀번호를 알 수 없게 하기 위해서라는 것을 알았다.
- Jwt 토큰의 개념을 직접 코드를 짜보면서 습득할 수 있었다.
- 통과하는 테스트와 의미 있는 테스트는 다르다는 것을 배웠다.
- 테스트 코드를 작성하면서 모든 경우의 수를 고려해보는 것이 실무에서 중요하다는 것을 배웠다.
- 코드를 작성하고 테스트 도구를 직접 사용해보면서 테스트 도구의 필요성과 쓰임새를 알게 되었다.
- Postman 프로그램 사용법을 배우게 되었다.
- 눈에 한번에 들어오는 코드를 작성하는 것이 정말 중요하다는 것을 알게 되었다.
