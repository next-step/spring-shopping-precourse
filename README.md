# spring-shopping-precourse

## 구현할 기능

- [x] 상품을 등록한다.
- [x] 상품 목록과 개별 상품을 조회하고, 상품을 수정·삭제한다.
- [x] 상품 등록 요청을 검증하고, 잘못된 요청에는 JSON으로 오류를 응답한다.
- [x] 상품을 등록할 때 PurgoMalum API로 상품명의 비속어를 검사한다.
- [x] 상품을 수정할 때 요청과 상품명을 검증하고, 잘못된 요청에는 JSON으로 오류를 응답한다.
- [x] 이메일과 비밀번호로 회원을 등록하고 인증 토큰을 발급한다.
- [x] 로그인 요청의 이메일과 비밀번호를 확인하고 인증 토큰을 발급한다.
- [x] 인증된 회원이 자신의 위시 리스트를 조회하고 상품을 추가·삭제할 수 있게 한다.

## 아키텍처와 학습 목표

이 프로젝트는 클린 아키텍처를 처음 적용해 보는 실습이다. 의존성이 안쪽으로 향하도록 설계하고, 그 결과 유스케이스를 Spring, 데이터베이스, 외부 HTTP 서비스 없이 실행하고 테스트할 수 있는 이유를 이해하는 것이 목표다.

`POST /api/products`와 `PUT /api/products/{productId}`는 `name`, `price`, `imageUrl`을 JSON으로 받는다. 상품 서비스는 상품을 검증한 뒤 PurgoMalum으로 상품명을 검사하고, 통과한 상품을 저장한다. Spring MVC 컨트롤러는 `@Service`로 등록한 상품 서비스를 호출한다. Spring Data JPA 저장소와 PurgoMalum HTTP 클라이언트는 각각 서비스가 사용하는 인터페이스를 구현한다.

가격은 0보다 커야 하고, 이미지 URL은 호스트가 있는 HTTP 또는 HTTPS 주소여야 한다. 등록이 성공하면 `201 Created`와 생성된 상품을, 수정이 성공하면 `200 OK`와 수정된 상품을 반환한다. 입력이 잘못됐거나 비속어가 확인되면 `400 Bad Request`, 비속어 검사를 완료할 수 없으면 `503 Service Unavailable`과 오류 메시지를 JSON으로 반환한다.

`GET /api/products`는 ID 오름차순으로 상품 목록을, `GET /api/products/{productId}`는 상품 하나를 반환한다. `DELETE /api/products/{productId}`로 삭제에 성공하면 `204 No Content`를 반환한다. 상세 조회·수정·삭제 대상이 없으면 `404 Not Found`와 오류 메시지를 JSON으로 반환한다.

`POST /api/members/register`와 `POST /api/members/login`은 `email`, `password`를 JSON으로 받는다. 이메일 앞뒤 공백과 대소문자는 구분하지 않는다. 비밀번호는 공백만으로 구성할 수 없고 UTF-8 기준 최대 72바이트이며, BCrypt 해시로 저장한다. 가입 성공 시 `201 Created`, 로그인 성공 시 `200 OK`와 함께 `{"token":"…"}`을 반환한다. 가입 입력이 잘못되면 `400`, 이미 가입된 이메일이면 `409`, 로그인 정보가 일치하지 않으면 `401`을 반환한다. 가입과 로그인은 같은 방식으로 랜덤 토큰을 발급하며, SQLite에는 토큰의 SHA-256 해시와 만료 시각을 저장한다. 토큰의 기본 유효기간은 24시간이며 `shopping.auth.token-ttl`로 설정한다.

위시 리스트 요청에는 `Authorization: Bearer <token>` 헤더가 필요하다. `GET /api/wishes`는 본인의 항목과 상품 정보를 조회하고, `POST /api/wishes`는 `productId`를 받아 `201 Created`와 `wishId`, `productId`를 반환한다. `DELETE /api/wishes/{wishId}`로 본인의 항목을 삭제하면 `204 No Content`를 반환한다. 토큰이 유효하지 않으면 `401`, 같은 상품을 다시 추가하면 `409`, 추가할 상품이나 삭제할 본인 항목이 없으면 `404`를 반환한다. 상품 삭제 시 SQLite 외래 키로 해당 상품의 위시 항목을 함께 삭제한다.

로컬 데이터베이스는 SQLite를 사용한다. 앱을 실행한 디렉터리에 `shopping.db`가 생성되며, 상품 테이블은 Hibernate의 `ddl-auto=update`로, 회원·토큰·위시 테이블은 `schema.sql`로 생성한다. 상품명 15자 제한은 애플리케이션에서 적용한다.

## 기능 구현 순서

기능마다 다음 순서를 반복한다.

1. 기능의 동작과 성공·실패 시나리오를 정의한다.
2. 클린 아키텍처에서 기능의 경계와 의존성 방향을 정한다.
3. 기능에 필요한 도메인 객체와 각 객체의 책임, 객체 간 관계를 정한다.
4. JUnit과 AssertJ로 첫 번째 동작을 검증하는 테스트를 작성한다.
5. 테스트를 통과하도록 구현한다. 남은 시나리오도 테스트 작성과 구현을 반복하고, 기능 단위로 커밋한다.

애플리케이션과 테스트 코드는 학습자가 직접 작성한다. AI는 [AGENTS.md](AGENTS.md)에 따라 설계 논의, 개념 설명, 테스트 시나리오 검토, 코드 리뷰를 돕는다.

## AI 활용 기록

- Codex로 프리코스 가이드 두 개를 읽고, 기능 목록과 구현 전략 초안을 작성했다. 논의에서 정한 아키텍처와 기능 구현 순서도 문서에 정리했다. 이후 AI를 어떻게 활용했는지, 직접 수정한 코드와 배운 점은 작업하면서 기록한다.
- 로컬 데이터베이스를 SQLite로 설정하고 Flyway 의존성을 제거했다. 상품명 자체의 규칙과 외부 비속어 검사의 책임을 어디에 둘지 논의했다.
- 학습자가 `ProductName` 레코드에 빈 이름, 공백 포함 15자 제한, 허용 문자 검사를 구현하고 JUnit과 AssertJ로 거절 사례를 작성했다. Codex와 생성자 예외를 검증하는 위치와 하나의 테스트를 여러 입력으로 실행하는 방법을 살펴봤다. 다음 구현은 PurgoMalum API 연동이다.
- 비속어 검사 인터페이스와 PurgoMalum HTTP 구현체를 작성하고, 검사 결과와 서비스 호출 실패를 구분했다.
- 상품 도메인, 등록 유스케이스, JPA 저장소, HTTP API를 연결했다. 로컬 모의 서버와 SQLite를 사용해 등록 성공 및 실패 흐름을 검증했다.
- 상품 등록 서비스는 `@Service`로 등록하고, 엔티티 변환과 저장을 Spring Data JPA 저장소에 모았다.
- 상품 목록·상세 조회, 수정, 삭제를 연결했다. 등록과 수정에서 상품 검증과 비속어 검사 로직을 공유한다.
- 학습자가 회원·인증과 위시 리스트 구현 및 전체 동작 검증을 Codex에 위임했다. Codex는 인증 정보와 위시 리스트의 소유권을 분리하고, 상품 삭제 시 위시 항목이 SQLite 외래 키로 실제 삭제되는지 HTTP 테스트로 확인했다. 자동 테스트는 동작별 시나리오를 한 곳에서 검증하도록 구성했다.
