# 쇼핑 (spring-shopping-precourse)

온라인 쇼핑몰의 상품·회원·위시 리스트 HTTP API를 스프링 부트로 구현한다. 요청과 응답은 JSON으로 주고받는다.

## 기능 목록

### 1. 상품
- [x] 상품을 생성한다 (이름, 가격, 이미지 URL) → 201
- [x] 상품 하나를 조회한다 → 200, 없으면 404
- [x] 상품 목록을 조회한다 → 200
- [x] 상품을 수정한다 → 200, 없으면 404
- [x] 상품을 삭제한다 → 204, 없으면 404

### 2. 상품 유효성 검사 (실패 시 400)
- [x] 이름은 비어 있을 수 없고, 공백 포함 최대 15자다
- [x] 이름에는 ( ) [ ] + - & / _ 외의 특수 문자를 쓸 수 없다
- [x] 이름에 비속어가 있으면 안 된다 (PurgoMalum API로 검사)
- [x] 가격은 0 이상이어야 한다
- [x] 이미지 URL은 http:// 또는 https://로 시작해야 한다

### 3. 회원
- [x] 이메일과 비밀번호로 가입하고 토큰을 받는다 → 201
- [x] 이메일 형식이 틀리거나, 비밀번호가 비어 있거나, 이미 가입된 이메일이면 400
- [x] 로그인에 성공하면 토큰을 받는다 → 200
- [x] 이메일이나 비밀번호가 틀리면 401
- [x] 비밀번호는 원문이 아닌 해시값으로 저장한다

### 4. 인증
- [x] `Authorization: Bearer {토큰}` 헤더로 로그인한 회원을 찾는다
- [x] 헤더가 없거나 토큰이 틀리면 401

### 5. 위시 리스트 (로그인 필요)
- [x] 위시 리스트에 상품을 추가한다 → 201, 없는 상품이면 404
- [x] 이미 담은 상품을 다시 담으면 400
- [x] 내 위시 리스트를 조회한다 → 200
- [x] 위시를 삭제한다 → 204, 없으면 404, 다른 회원의 위시면 403

### 6. 오류 응답
- [x] 모든 오류는 같은 형식으로 응답한다: `{ "message": "오류 내용" }`
- [x] 비속어 검사 API에 연결할 수 없으면 503

## 구현 전략

### 구조
- 기능별 패키지: `product`, `member`, `wish`, `common`
- 계층: Controller(요청·응답) → Service(흐름·트랜잭션) → 도메인(검증 규칙) → Repository(JPA)
- 검증 규칙은 도메인 객체(`ProductName` 등)에 두어 스프링 없이 단위 테스트할 수 있게 한다

### 데이터
- DB는 H2 인메모리, 테이블은 Flyway 마이그레이션으로 만든다 (V1 상품, V2 회원, V3 위시)
- 상품을 삭제하면 그 상품이 담긴 위시도 함께 삭제한다

### 인증
- 로그인할 때마다 UUID 토큰을 새로 발급해 회원 테이블에 저장한다
- 컨트롤러에서는 `@LoginMember` 파라미터로 로그인한 회원을 받는다 (ArgumentResolver)

### 외부 API
- 비속어 검사는 `ProfanityChecker` 인터페이스로 분리한다
- 실제로는 PurgoMalum을 호출하고, 테스트에서는 가짜 구현을 써서 외부 API 상태와 상관없이 테스트가 통과하게 한다

### 테스트
- 도메인 규칙: JUnit5 + AssertJ 단위 테스트 (`@ParameterizedTest`로 경계값 검사)
- API: `@SpringBootTest` + MockMvc로 요청부터 응답 코드·본문까지 검사

### 프로그래밍 요구사항 지키는 법
- 들여쓰기 2단계 이하: 조건문 안의 로직은 메서드로 분리한다
- 메서드 15줄 이하, else·switch·3항 연산자 금지: `if`에서 바로 return하거나 throw한다

### 요구사항에 없어 직접 정한 것
- 상품 생성·수정·삭제는 인증 없이 허용한다 (관리자 개념이 요구사항에 없음)
- 가격 0원(무료 상품)을 허용한다
- 같은 상품을 위시에 중복으로 담을 수 없다
- 비속어 검사는 PurgoMalum 기준을 따른다 (영어 비속어만 걸러진다)
- JSON 문법 오류나 숫자가 아닌 ID 같은 잘못된 요청도 `{ "message": … }` 형식의 400으로 응답한다
- 비밀번호는 외부 라이브러리 없이 SHA-256 해시로 저장한다 (실제 서비스라면 솔트를 쓰는 BCrypt 등을 써야 한다)
- 토큰이 없거나 틀리면 401, 다른 회원의 위시를 삭제하려 하면 403으로 구분한다

## AI 활용 기록

### 사용한 도구
- Claude (Anthropic)

### 활용 방식
| 단계 | 내용 | AI 활용 |
|---|---|---|
| 0~1 | 개발 환경(JDK 21), 포크·클론, 기능 목록 작성 | 진행 순서와 README 구성을 안내받음 |
| 2 | `ProductName` 이름 검증 | AI가 제시한 코드를 바탕으로 직접 작성, 테스트 메서드 이름이 숫자로 시작해 컴파일되지 않던 오류를 함께 수정 |
| 3 | `Product` 엔티티, Flyway SQL | 뼈대와 TODO별 예시를 받아 직접 조립, AI 리뷰로 `change` 메서드 누락·오타 수정 |
| 4~5 | 공통 오류 응답, 비속어 검사 연동 | 힌트를 받아 직접 작성, AI 리뷰로 503 처리 누락과 패키지 대소문자 문제 수정 |
| 6 | 상품 API (Service·Controller) | AI 예시 코드를 이해하고 적용 |
| 6~9 | 상품 API 테스트, 회원·인증·위시 리스트 | 요청에 따라 AI가 구현하고 테스트를 통과시킨 뒤 커밋 (커밋에 `Co-Authored-By: Claude` 표시) |

### 직접 확인하고 배운 점
- 개발 환경: 템플릿이 Java 21과 Gradle 9를 쓰는데 처음에 맥이 Java 18이라 빌드가 되지 않았다. JDK를 21로 바꾸고 터미널(JAVA_HOME)과 IntelliJ(SDK, Gradle JVM) 설정이 따로라는 것을 알게 되었다.
- 외장 볼륨에서 `./gradlew`가 `Operation not supported`로 실패했는데, 파일 잠금을 지원하지 않는 디스크 형식 때문이었다. 프로젝트를 내장 디스크로 옮겨 해결했다.
- 자바 기본기: 패키지 이름은 폴더 경로와 같아야 하고(`pruduct`, `Common` 같은 오타·대소문자 문제를 여러 번 겪음), 메서드 이름은 숫자로 시작할 수 없다는 것을 컴파일 오류로 배웠다.
- `private static final` 상수, `final` 필드, 값이 없는 경우를 구분하려고 가격을 `int`가 아닌 `Integer`로 받는 이유, 데이터만 담는 `record`를 이해했다.
- `Product`의 생성자와 `update`가 같은 검증을 하도록 `change` 메서드로 중복을 없애고, 검증을 모두 마친 뒤에 값을 넣어야 객체가 반쯤 바뀐 상태로 남지 않는다는 것을 테스트로 확인했다.
- `@RestControllerAdvice`로 예외를 상태 코드와 `{ "message": … }` 응답으로 바꾸는 방법, 외부 API(PurgoMalum)를 인터페이스로 분리해 테스트에서는 가짜 구현을 쓰는 이유를 알게 되었다.
- 회원·인증·위시 리스트(6~9단계)는 AI와 협업하여  구현했기 때문에, 코드를 다시 읽으며 `@LoginMember`와 ArgumentResolver가 토큰으로 회원을 찾는 흐름을 직접 설명할 수 있도록 공부할 예정이다.

## 과제 진행 소감
- 처음에는 스프링으로 API를 만드는 전반적인 지식이 부족해서, 무엇부터 해야 할지 몰라 단계마다 물어보며 초안을 만들었다.
- 패키지 위치, 오타, 디스크 형식처럼 사소해 보이는 문제에서 오래 막혔고, 그 과정에서 아직 기본기가 많이 부족하다는 것을 느꼈다.
- 앞부분은 힌트와 예시를 받아 직접 작성하고 리뷰를 받으며 고쳤지만, 뒷부분은 시간이 부족해 AI와 협업하여 구현을 하였다. 다 맡긴 것은 아니지만 스스로 끝까지 해내지 못한 점이 아쉽다.
- 다음에는 기능 목록을 먼저 정리하고 작은 단위로 직접 구현해 보면서, AI는 막혔을 때 확인하는 용도로 쓰고 싶다.
