# spring-shopping-precourse

Spring Boot로 상품, 회원, 위시리스트 API를 구현한다. 애플리케이션 API의 요청과 응답은 본문이 있는 경우 JSON으로 처리한다.

## 구현할 기능 목록

체크박스 하나를 커밋 하나로 잡는다. 아래 순서대로 작업하고, 각 커밋의 작업 범위와 검증 결과를 브리핑한다.

- [x] `docs: README.md에 구현할 기능 목록 및 구현 전략 추가` — 구현 순서, 검증 계획, AI 활용 및 학습 기록을 정리한다.
- [ ] `feat: 회원 가입 및 토큰 발급 구현` — `POST /api/members/register`로 이메일과 비밀번호를 검증하고 회원을 생성한 뒤 문자열 토큰을 발급한다. 계정 생성 완료, 가입 시 토큰 발급 보류.
- [x] `feat: 회원 로그인 및 토큰 발급 구현` — `POST /api/members/login`에서 이메일과 비밀번호를 확인한다. 인증에 성공하면 토큰을 발급하고 실패하면 오류를 응답한다.
- [x] `feat: 상품 등록 API 구현` — `POST /api/products`로 이름, 가격, 이미지 URL을 받는다. 이름의 길이·허용 문자·비속어를 검사한다. 이미지는 입력받은 URL로 관리한다.
- [x] `feat: 상품 단건 조회 API 구현` — `GET /api/products/{productId}`로 특정 상품을 조회한다.
- [x] `feat: 상품 목록 조회 API 구현` — `GET /api/products`로 등록된 상품 전체를 조회한다.
- [x] `feat: 상품 수정 API 구현` — `PUT /api/products/{productId}`로 특정 상품을 수정한다. 등록과 동일한 상품 이름 검증을 적용한다.
- [ ] `feat: 회원 위시리스트 상품 추가 구현` — `POST /api/wishes`에서 토큰으로 회원을 식별하고, 등록된 상품을 해당 회원의 위시리스트에 추가한다. 항목 저장 로직 완료, 인증·HTTP 연결과 중복 정책 보류.
- [ ] `feat: 회원 위시리스트 상품 조회 구현` — `GET /api/wishes`에서 인증된 회원이 자신의 위시리스트에 담은 상품 목록을 조회한다. 회원별 조회 로직 완료, 인증·HTTP 연결 보류.
- [ ] `feat: 회원 위시리스트 상품 삭제 구현` — `DELETE /api/wishes`에서 인증된 회원의 위시리스트에서 지정한 상품을 삭제한다. 담겨 있지 않은 상품을 삭제하면 오류를 응답한다. 회원별 항목 삭제 로직 완료, 인증·HTTP 연결과 삭제 식별자 전달 방식 보류.
- [ ] `feat: 상품 삭제 API 구현` — `DELETE /api/products/{productId}`로 특정 상품을 삭제한다. 기본 삭제 완료, 위시리스트에서 참조 중인 상품의 삭제 정책 보류.

### 구현 순서를 정한 이유

- 회원 가입에서 계정과 토큰 발급을 만들고, 로그인에서 인증 정보 확인과 토큰 발급을 연결한다. 회원 인증 흐름을 먼저 준비하는 순서로 잡았다.
- 상품 등록 후 단건·목록 조회를 구현하여 저장한 상품을 확인할 수 있게 한다. 이어서 수정 기능에 등록 시 만든 검증을 재사용한다.
- 회원과 상품이 준비되면 위시리스트를 구현한다. 추가 기능에서 토큰 검증과 회원별 항목 저장을 연결하고, 조회와 삭제에서 이를 활용한다.
- 상품 삭제는 마지막에 구현한다. 위시리스트에 담긴 상품을 삭제했을 때의 처리까지 함께 결정하고 반영한다.

커밋 제목은 `<type>: <한글 변경 요약>` 형식으로 작성한다. `feat`, `fix`, `docs`, `test` 등 영어 프리픽스를 사용하고, 제목은 변경 내용을 설명하는 짧은 구절로 쓰며 끝에 마침표를 붙이지 않는다. 본문이 필요하면 빈 줄 뒤에 변경 이유를 한글로 적고 각 줄을 100자 이내로 작성한다. [Git Commit Message Conventions](https://gist.github.com/stephenparish/9941e89d80e2bc58a153)

## 현재 구현 범위와 보류 항목

- 미정인 정책은 결정 후 구현한다. 비밀번호 최소 길이, 토큰 만료·로그아웃·해시 저장, 가격 범위, 추가 이미지 URL 검증, 공백만 있는 상품 이름의 처리, 위시리스트 중복·수량 정책과 상품 삭제 시 위시리스트 처리가 이에 해당한다.
- 가입은 이메일 형식과 필수값을 검사하고 계정을 저장한다. 비밀번호는 Spring Security의 PBKDF2로 해시한다. 가입 응답은 `{"memberId": 1}`이며 가입 시 토큰 발급은 보류한다.
- 로그인은 이메일과 비밀번호가 일치하면 `{"token": "..."}`을 반환한다. 토큰은 회원 ID와 함께 메모리에 저장하므로 애플리케이션을 종료하면 무효화된다.
- 이메일은 로그인 식별자로 사용하며 메모리 저장소에서 중복 여부를 확인한다. 가입 성공은 201, 중복 이메일은 409로 응답한다.
- `Email`, `Password`, `PasswordHash`, `ProductName` 값 객체가 형식과 필수값을 검사한다. DTO는 HTTP 경계에서 같은 규칙을 먼저 검사하고, 모델은 직접 생성되는 경우에도 유효한 상태를 보장한다.
- 회원, 상품, 위시리스트는 애플리케이션 메모리에 저장한다. 애플리케이션을 종료하면 저장한 데이터가 사라진다.
- 빌드에는 제공된 JPA·Flyway·H2·MySQL 의존성이 포함되어 실행 시 임베디드 H2가 초기화된다. 현재 모델과 저장소는 이를 사용하지 않으며 애플리케이션 데이터는 `Map`에 저장한다.
- 합의한 입력 검증, 비속어 검사와 메모리 저장소 동작을 JUnit과 AssertJ로 검증한다. 나머지 테스트 후보는 협의 후 추가한다.

- 상품 가격은 브리핑의 `Long` 정수로 저장하며 범위 제약은 추가하지 않는다. 이름은 문자·숫자·일반 공백과 지정 특수문자를 허용한다. `@Size`의 길이는 Java UTF-16 기준이다. 이미지 URL은 문자열로 받는다.
- 상품 등록과 수정에서 PurgoMalum의 `containsprofanity`를 호출한다. `shopping.profanity.base-url`로 호출 대상을 설정할 수 있다. 장애 시 재시도·우회·전용 상태 코드 정책은 보류하며 기본 예외를 전파한다.

- 위시리스트는 회원·상품을 참조하는 항목과 서비스 로직을 먼저 구현한다. HTTP API는 인증된 회원을 식별하는 토큰 검증을 연결한 뒤 제공한다. 수량과 중복 요청 처리 정책은 보류한다.

- 상품 삭제는 존재하는 상품을 삭제하고 204를 반환하며, 미존재 상품은 404를 반환한다. 위시리스트에 담긴 상품을 삭제할 때의 연관 항목 처리는 정책 결정 후 구현한다.
- 현재 HTTP API는 회원 가입·로그인과 상품 CRUD다. 로그인 토큰 발급까지 구현했으며, 위시리스트 HTTP API, 요청 토큰 검증, 상품 관리 권한은 후속 결정과 연결이 필요하다.

## 패키지 구조

- `controller`는 HTTP 요청과 응답을 처리한다.
- `model`은 회원, 상품, 위시리스트 데이터와 값 객체를 표현하고 유효한 상태를 보장한다.
- `service`는 애플리케이션의 작업 흐름을 처리한다.
- `repository`는 `Map`에 데이터를 저장하고 조회하며 `AtomicLong`으로 ID를 생성한다.
- `dto`는 JSON 요청과 응답에 사용하는 데이터를 담는다.
- `validation`과 `config`는 비속어 검사와 애플리케이션 설정을 관리한다.

## 구현 전략

### 회원과 인증

- 회원은 이메일과 비밀번호로 인증할 수 있는 계정과 자신의 위시리스트를 가진다. 가입 시 비밀번호 해시를 저장하고, 로그인 시 입력값을 저장된 해시와 비교한다.
- `Email` 값 객체는 `null`, 빈 값, 공백과 `@`가 없거나 로컬 부분·도메인이 비어 있는 값을 거부한다. DTO의 `@Pattern`도 `Email.PATTERN`을 사용하여 HTTP 검증과 모델 규칙이 달라지지 않게 한다.
- `Password`는 현재 확정된 규칙인 `null`만 거부하고, `PasswordHash`는 PBKDF2 결과가 비어 있지 않음을 보장한다. 비밀번호 최소 길이는 결정 후 `Password`에 추가한다.
- 비밀번호는 최소 길이를 검사한다. 이 과제의 최솟값은 아직 정하지 않았다. 이메일과 비밀번호로 로그인하는 흐름을 기준으로 15자를 초안으로 제안한다. NIST는 비밀번호를 단일 인증 요소로 쓸 때 최소 15자를 요구하며, 문자 종류 조합 규칙을 부과하지 않도록 한다. [NIST SP 800-63B-4](https://pages.nist.gov/800-63-4/sp800-63b.html)
- 무작위 토큰과 서명된 JWT를 비교한 뒤, 현재 범위에는 서버에 저장하는 무작위 토큰을 선택했다. `SecureRandom`으로 32바이트를 생성하고 패딩 없는 Base64 URL 형식으로 인코딩한다. 로그인에 성공한 뒤에만 토큰을 생성하며 회원 ID와 함께 메모리에 저장한다.
- 무작위 토큰은 서버에서 저장 여부와 연결된 회원을 확인할 수 있고 기록을 제거해 무효화하기 쉽다. 서명된 JWT는 서버 저장 없이 내용을 검증할 수 있지만, 만료 전 개별 토큰 취소에는 별도 상태가 필요하다. 토큰 만료 시간, 로그아웃, 저장 시 해시 적용과 `Authorization: Bearer <token>` 검증은 정책 결정 후 구현한다. [OWASP 세션 관리 가이드](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [RFC 7519](https://www.rfc-editor.org/rfc/rfc7519)

### 상품

- Spring MVC와 Jakarta Validation을 활용한다. 컨트롤러가 JSON을 받고 응답하고, 상품 저장과 조회는 메모리 저장소에 맡긴다.
- `ProductName` 값 객체가 이름을 공백 포함 1~15자로 제한한다. 허용하는 특수문자는 `(`, `)`, `[`, `]`, `+`, `-`, `&`, `/`, `_`이며 등록과 수정에서 같은 객체를 사용한다.
- `Product`는 이름, 가격, 이미지 URL이 `null`인 상태로 생성되거나 수정되지 않게 한다. 가격 범위와 이미지 URL 형식은 정하지 않았으므로 검사하지 않는다.
- 길이와 허용 문자를 먼저 검사한다. 통과한 이름을 URL 인코딩하여 PurgoMalum의 `GET /service/containsprofanity?text=...`에 전달하고, 본문이 `true`이면 검증 오류로 처리한다. 연결 실패·시간 초과·예상 밖 응답은 검증 서비스 오류로 처리하여 저장을 중단하는 방안을 제안한다. [PurgoMalum API](https://www.purgomalum.com/)
- 상품 이름에서 공백만 있는 문자열을 허용할지, 이미지 URL과 가격의 세부 검증 기준을 어떻게 잡을지 등록 기능 구현 전에 정한다.

### 위시리스트

- 추가·삭제·조회에서 토큰을 공통으로 검증한 뒤, 확인된 회원의 항목만 다룬다. 상품 추가 전에 등록된 상품인지 확인한다.
- Java의 `List`는 순서가 있는 목록으로 일반적으로 중복을 허용한다. `Set`은 중복을 허용하지 않는다. `Map`은 상품 ID 같은 키에 수량 같은 값을 연결할 수 있다. 응답에 상품 목록을 담을 때는 `List`를 사용할 수 있다. [Java List](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/List.html), [Java Set](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Set.html), [Java Map](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Map.html)
- 사용자 요구사항의 조회·추가·삭제 흐름을 기준으로, 회원별 상품을 한 번만 저장하고 수량은 두지 않는 방안을 제안한다. 이 경우 메모리 저장소에서 회원 ID와 상품 ID가 같은 항목의 중복을 검사할 수 있다. 수량을 도입한다면 재추가 시 증가량과 삭제 시 한 개 차감 또는 항목 전체 제거 중 어떤 동작을 할지 함께 정한다.
- 위시리스트 구현 전에 재추가 요청의 응답, 삭제할 상품 ID의 전달 방식, 위시리스트에 담긴 상품이 상품 API에서 삭제되는 경우의 처리를 정한다.

## 테스트 계획

JUnit과 AssertJ로 구현한 기능의 동작을 검증한다. DTO 입력 검증뿐 아니라 값 객체와 모델 생성자를 직접 호출하여 HTTP를 거치지 않아도 잘못된 상태가 차단되는지 확인한다. 나머지는 협의할 테스트 후보다.

| 대상 | 테스트 후보 |
| --- | --- |
| 상품 | 등록·조회·수정·삭제의 정상 흐름, 이름 1자·15자 경계와 0자·16자 실패, 허용 문자와 금지 문자, 비속어 검출 및 외부 API 오류 |
| 회원 | 가입·로그인 성공 시 토큰 발급, 이메일 형식 오류, 최소 길이 미달, 일치하지 않는 인증 정보 |
| 위시리스트 | 회원별 추가·조회·삭제, 유효한 토큰이 없는 요청 거절, 다른 회원의 항목 격리, 미등록 상품 추가와 미포함 상품 삭제 실패 |
| 저장소 | 회원 ID 생성과 이메일 조회, 상품 저장·조회·삭제와 빈 목록, 회원별 위시리스트 격리와 삭제 |
| 모델 | 이메일·비밀번호·상품 이름 규칙, 회원·상품·위시리스트·토큰의 필수값과 ID 검증 |

비속어 검사 테스트는 외부 API 응답을 제어하여 실제 외부 서비스에 의존하지 않는다.
