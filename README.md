# spring-shopping-precourse
캠퍼스 프로그래밍 3기 - 프리코스: 쇼핑 API

## 기능 요구사항
- 온라인 쇼핑몰을 위한 간단한 HTTP API
- HTTP 요청과 응답은 JSON으로 주고 받음
- 스프링 프레임워크를 사용해 웹 애플리케이션으로 구현

### 회원
- [x] 회원가입 기능
  - [x] 이메일과 비밀번호를 기입해 회원가입한다.
    - [x] 회원가입·로그인 시 이메일과 비밀번호는 필수이며, 누락될 경우 입력 검증 실패로 처리한다.
    - [x] 이메일 유효성 검사
      - [x] 앞뒤 공백을 제거한 뒤 검증하며, 빈 값이거나 내부에 공백이 있으면 실패로 처리한다.
      - [x] `사용자명@도메인` 형태의 유효한 이메일 주소만 허용한다.
      - [x] 앞뒤 공백 제거 후 길이는 최대 254자여야 한다.
      - [x] 대소문자를 구분한다.
      - [x] 이미 회원가입한 이메일은 다시 사용할 수 없다.
    - [x] 비밀번호 유효성 검사
      - [x] 공백을 허용하지 않는다.
      - [x] 길이는 5자 이상 16자 이하여야 한다.
  - [x] 회원가입에 성공하면 인증 토큰을 발급받는다.
- [x] 로그인 기능
  - [x] 이메일 중복 검사를 제외하고 회원가입과 동일한 이메일·비밀번호 유효성 검사를 수행한다.
  - [x] 이메일과 비밀번호를 검증받아 로그인한다.
  - [x] 로그인에 성공하면 인증 토큰을 발급받는다.
  - [x] 미가입 이메일과 비밀번호 불일치는 동일한 인증 실패로 처리한다.

### 토큰 인증
- [x] 예측하기 어려운 임의의 문자열을 사용한다.
- [x] 서버에서 토큰에 연결된 회원과 만료 시각을 관리한다.
- [x] 인증 토큰은 `Authorization: Bearer <토큰>` 헤더로 전달한다.
- [x] 토큰은 발급 시점부터 1시간 동안 유효하며, 사용해도 만료 시각을 연장하지 않는다.
- [x] 재로그인 시 기존 토큰도 각자의 만료 시각까지 유효하다.
- [x] 토큰 누락·형식 오류·미등록·만료 시 인증 실패로 처리한다.
- [x] 유효한 토큰에 연결된 회원을 현재 요청의 사용자로 식별한다.

### 상품
- [x] 상품 추가 기능
  - [x] 이름, 가격, 이미지 URL(파일 업로드 X)을 포함한다.
  - [x] 상품 이름 유효성 검사
    - [x] 상품 이름은 null, 빈 문자열, 공백만 있는 문자열일 수 없다.
    - [x] 상품 이름은 공백을 포함하여 최대 15자까지 입력할 수 있다.
    - [x] 상품 이름에는 아래 특수 문자만 사용할 수 있다.
      - [x] 가능한 특수문자: (), [], +, -, &, /, _
      - [x] 그 외 특수문자는 사용할 수 없다.
    - [x] 상품 이름은 비속어를 포함할 수 없다.
      - [x] [PurgoMalum](https://www.purgomalum.com/) API를 호출해 비속어 포함 여부를 검사한다.
      - [x] 비속어가 포함되면 입력값 검증 실패로 처리한다.
      - [x] API 오류·시간 초과·해석할 수 없는 응답은 비속어 검사 불가로 구분해 오류 응답을 반환한다.
      - [x] 비속어 검사 불가 시 상품을 저장하지 않으며, 수정 요청은 기존 상품 정보를 유지한다.
  - [x] 상품 가격 유효성 검사
    - [x] 가격은 필수이며, 0원·음수·소수는 허용하지 않는다.
    - [x] 상품 가격은 1원 이상 2,147,483,647원 이하의 정수만 허용한다.
  - [x] 상품 이미지 유효성 검사
    - [x] 상품 이미지 URL은 필수이며, 호스트가 있는 http 또는 https URL만 허용한다.
    - [x] URL 형식을 검증하되, 실제 이미지 존재 여부를 확인하는 외부 요청은 하지 않는다.
  - [x] 유효성 검사 실패 시 오류 응답을 반환하고 상품을 저장하지 않는다.
- [x] 상품 조회 기능
  - [x] 상품 id가 제공될 경우 특정 상품의 정보를 조회한다.
  - [x] 상품 id가 제공되지 않을 경우 모든 상품의 목록을 조회한다.
  - [x] 존재하지 않는 상품 id로 조회를 요청하면 실패로 처리한다.
- [x] 상품 수정 기능
  - [x] 상품 id로 조회되는 기존 상품의 정보를 수정한다.
  - [x] 이름, 가격, 이미지 URL을 모두 전달받고 상품 추가와 동일한 유효성 검사를 수행한다.
  - [x] 유효성 검사 실패 시 오류 응답을 반환하고 상품을 변경하지 않는다.
  - [x] 존재하지 않는 상품 id로 수정을 요청하면 실패로 처리한다.
- [x] 상품 삭제 기능
  - [x] 상품 id로 특정 상품을 삭제한다.
  - [x] 존재하지 않는 상품 id로 삭제를 요청하면 실패로 처리한다.

### 위시리스트
- [x] 인증된 사용자가 아니라면 위시리스트 기능을 사용할 수 없다.
- [x] 위시리스트 상품 목록 조회 기능
  - [x] 자신이 아닌 다른 회원의 위시 목록 조회를 요청하면 실패로 처리한다.
  - [x] 등록된 상품이 없으면 빈 목록을 반환한다.
- [x] 위시리스트 상품 추가 기능
  - [x] 자신이 아닌 다른 회원의 위시 상품 추가를 요청하면 실패로 처리한다.
  - [x] 본인의 위시리스트에 이미 등록된 상품을 추가하면 실패로 처리한다.
  - [x] 존재하지 않는 상품을 추가하면 실패로 처리한다.
- [x] 위시리스트 상품 삭제 기능
  - [x] 존재하지 않는 위시리스트 항목의 삭제를 요청하면 실패로 처리한다.
  - [x] 자신이 아닌 다른 회원의 상품 삭제를 요청하면 실패로 처리한다.
  - [x] 원본 상품이 삭제될 시 해당 상품을 담은 모든 회원의 위시리스트 항목도 함께 삭제한다.

## 구현 전략
- README에는 기능의 행동 규칙을, API 명세에는 요청·응답 형식과 상태 코드를 기록한다.
- 전체 기능의 계층을 한꺼번에 구현하지 않고, 아래 과정을 기능 하나마다 반복한다.

### 기능별 구현 흐름
1. 구현할 기능의 요구사항을 확인하고, 해당 기능에 필요한 미결정 정책을 정해 기록한다.
2. 해당 기능의 API 명세를 성공·실패 조건과 함께 작성하거나 보완한다.
3. 요구사항을 바탕으로 필요한 도메인 구조를 설계하고, 클래스별 책임과 요구사항을 정리한다.
4. 정리한 요구사항을 기준으로 AI로 테스트 코드를 작성하고 검수한다.
5. 테스트를 실행해 구현하려는 동작이 없어 실패하는지 확인한다.
6. 검수한 테스트를 바탕으로 AI로 프로덕션 코드를 작성한다. 기능 안에서는 도메인 -> 서비스/레포지토리 -> 컨트롤러 순서로 진행한다.
7. 프로덕션 코드를 검수하고, 테스트를 실행해 통과하는지 확인한다.
8. 필요한 리팩터링을 수행하고 관련 테스트를 다시 실행한다.
9. 기능 목록의 완료 상태와 AI 활용 기록을 갱신하고, 기능 단위로 커밋한다.

### 테스트 코드 작성 지침
- JUnit과 AssertJ로 기능 목록의 동작을 검증한다.
- 단위 테스트는 해당 객체가 보장해야 하는 책임에 집중한다.
- 동일한 검증 규칙을 클래스마다 불필요하게 반복하지 않는다. 다만 API 테스트에서는 검증 실패가 오류 응답으로 연결되는지 등 계층 간 연결을 확인한다.
- 정상 케이스, 예외 케이스, 경계값을 테스트한다.
- 라이브러리 자체의 동작은 테스트하지 않는다.
- 테스트는 해당 객체의 사용 설명서다. 각 테스트는 객체가 보장하는 하나의 계약을 드러내야 한다.
- 같은 계약을 검증하는 사례는 대표값과 의미 있는 경계값만 남긴다. 단순 getter 확인이나 입력값만 바꾼 반복 사례는 추가하지 않는다.
- 작성 후 각 테스트가 설명하는 책임을 검토한다. 다른 테스트와 중복되거나, 해당 객체의 책임이 아니거나, 이름에 적힌 동작을 실제로 검증하지 못하는 테스트는 제거한다.

### 프로덕션 코드 작성 지침
- Google Java Style Guide를 기본으로 하되, 들여쓰기는 4칸으로 한다.
- 중첩 깊이는 최대 2단계까지만 허용한다.
- 메서드의 길이가 15줄을 넘어가지 않도록 구현한다.
- 메서드가 한 가지 일만 하도록 작성한다.
- else 또는 switch문을 사용하지 않는다.
- 3항 연산자를 사용하지 않는다.
- AI가 생성한 코드는 동작과 설계 의도를 이해한 뒤 반영한다.
- 도메인이 책임질 로직은 도메인에서 처리하고 단위 테스트로 검증한다.
- 조회·정렬·필터링은 DB를 활용하되, 업무 판단 로직을 복잡한 SQL로 옮기지 않는다.
- 메서드 내부는 작업 맥락에 따라 개행해 읽기 쉽게 작성한다.
