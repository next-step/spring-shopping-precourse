# 🛒 쇼핑 프리코스

## 1. 기능 목록

### 1.1. 상품 관리

**상품 등록**
- [x] 상품 이름, 가격, 이미지 URL을 입력받아 상품을 등록한다.
- [x] 상품 등록에 성공하면 상품 정보를 저장한다.

**상품 조회**
- [x] 상품 ID로 특정 상품의 정보를 조회한다.
- [x] 등록된 모든 상품의 목록을 조회한다.
- [x] 존재하지 않는 상품 ID로 조회하면 오류를 반환한다.

**상품 수정**
- [x] 상품 ID로 기존 상품의 이름, 가격, 이미지 URL을 수정한다.
- [x] 상품 수정 시에도 상품 이름에 대한 유효성 검사를 수행한다.
- [x] 존재하지 않는 상품 ID로 수정하면 오류를 반환한다.

**상품 삭제**
- [x] 상품 ID로 특정 상품을 삭제한다.
- [x] 존재하지 않는 상품 ID로 삭제하면 오류를 반환한다.

### 1.2. 상품 유효성 검사 및 예외 처리

**상품 이름 길이 검증**
- [x] 상품 이름은 공백을 포함하여 최대 15자까지 허용한다.
- [x] 상품 이름이 15자를 초과하면 등록 및 수정을 거부한다.

**특수문자 검증**
- [x] 상품 이름에 `( ) [ ] + - & / _` 특수문자를 허용한다.
- [x] 허용되지 않은 특수문자가 포함되면 등록 및 수정을 거부한다.

**비속어 검증**
- [x] PurgoMalum API를 호출하여 상품 이름의 비속어 포함 여부를 검사한다.
- [x] 비속어가 포함된 상품 이름은 등록 및 수정을 거부한다.

**입력값 검증**
- [x] 상품 이름이 비어 있거나 공백만 포함하면 등록 및 수정을 거부한다.
- [x] 상품 가격이 0원 이하이면 등록 및 수정을 거부한다.
- [x] 상품 이미지 URL이 비어 있으면 등록 및 수정을 거부한다.
- [x] 입력값이 유효하지 않으면 적절한 오류 응답을 반환한다.

### 1.3. 회원가입 및 로그인

**회원가입**
- [x] 이메일과 비밀번호를 입력받아 회원을 등록한다.
- [x] 이미 가입된 이메일이면 회원가입을 거부한다.
- [x] 비밀번호를 해시 처리하여 저장한다.
- [x] 회원가입에 성공하면 인증 토큰을 발급한다.

**로그인**
- [x] 이메일과 비밀번호를 입력받아 회원을 인증한다.
- [x] 이메일과 비밀번호가 일치하면 인증 토큰을 발급한다.
- [x] 이메일 또는 비밀번호가 일치하지 않으면 인증을 거부한다.

**인증 토큰**
- [x] UUID 기반 인증 토큰을 생성한다.
- [x] 인증이 필요한 요청에서 토큰의 유효성을 확인한다.
- [x] 유효하지 않거나 누락된 토큰으로 위시 리스트에 접근하면 요청을 거부한다.

### 1.4. 위시 리스트

**상품 추가**
- [x] 인증된 사용자는 자신의 위시 리스트에 상품을 추가할 수 있다.
- [x] 존재하지 않는 상품은 위시 리스트에 추가할 수 없다.
- [x] 이미 추가한 상품을 중복 등록하면 거부한다.

**상품 조회**
- [x] 인증된 사용자는 자신의 위시 리스트에 등록된 상품 목록을 조회할 수 있다.

**상품 삭제**
- [x] 인증된 사용자는 위시 리스트 ID로 자신의 위시 리스트 항목을 삭제할 수 있다.
- [x] 존재하지 않는 위시 리스트 ID로 삭제하면 오류를 반환한다.
- [x] 다른 사용자의 위시 리스트 항목을 삭제할 수 없다.

### 1.5. API 구현

**회원 API**
- [x] `POST /api/members/register` — 회원가입 및 토큰 발급
- [x] `POST /api/members/login` — 로그인 및 토큰 발급

**상품 API**
- [x] `POST /api/products` — 상품 등록
- [x] `GET /api/products/{productId}` — 상품 조회
- [x] `GET /api/products` — 전체 상품 조회
- [x] `PUT /api/products/{productId}` — 상품 수정
- [x] `DELETE /api/products/{productId}` — 상품 삭제

**위시 리스트 API**
- [x] `POST /api/wishes` — 위시 리스트 상품 추가
- [x] `GET /api/wishes` — 위시 리스트 상품 조회
- [x] `DELETE /api/wishes/{wishId}` — 위시 리스트 상품 삭제

## 2. 구현 전략

### 2.1. 프로젝트 구조

Spring 기반 계층형 구조로 구현한다.

- **Controller:** HTTP 요청을 받고 JSON 응답을 반환한다.
- **Service:** 상품 관리, 회원 인증, 위시 리스트의 비즈니스 로직을 처리한다.
- **Repository:** 데이터 저장 및 조회를 담당한다.
- **DTO:** 요청과 응답에 필요한 데이터를 전달한다.
- **Domain:** 상품, 회원, 위시 리스트의 데이터와 핵심 규칙을 표현한다.

**선택 이유:** 각 클래스의 책임을 분리하여 코드 중복을 줄이고, 메서드 15줄 제한 및 들여쓰기 2단계 제한을 지키기 쉽게 하기 위해서다.

### 2.2. 상품 유효성 검사

상품 등록과 수정에 공통 검증 로직을 적용한다.

- 상품 이름 길이, 특수문자, 비속어 검사를 각각 분리한다.
- 잘못된 입력값은 예외를 발생시켜 처리한다.
- 비속어 검사는 PurgoMalum API를 이용한다.
- 외부 API 호출 로직을 분리하여 테스트 시 대체할 수 있도록 한다.

**선택 이유:** 등록과 수정에 동일한 규칙을 적용하고, 각 검증 기능을 독립적으로 테스트하기 위해서다.

### 2.3. 회원 인증

- 회원은 이메일과 비밀번호로 가입한다.
- 비밀번호는 안전한 단방향 해시 방식으로 저장한다.
- 인증 토큰은 UUID로 생성하고 서버에 저장한다.
- 인증이 필요한 요청에서는 전달된 토큰으로 사용자를 식별한다.

**선택 이유:** 토큰 생성 방식이 자유로운 과제이므로, 인증 흐름을 먼저 이해하고 구현하기 쉬운 UUID 방식을 선택한다.

### 2.4. 데이터 관리

- 상품, 회원, 위시 리스트 데이터를 구분하여 저장한다.
- 위시 리스트 항목은 회원과 상품을 참조하도록 설계한다.
- 데이터 저장 및 조회는 Repository를 통해 처리한다.
- 실제 저장 기술과 테이블 생성 방식은 프로젝트의 기존 설정을 확인하여 결정한다.

**선택 이유:** 데이터 접근 로직과 비즈니스 로직을 분리하고, 회원별 위시 리스트를 관리하기 위해서다.

### 2.5. 예외 처리

Spring의 `@RestControllerAdvice`를 활용하여 오류 응답을 공통으로 처리한다.

| 상황 | HTTP 상태 코드 |
|---|---|
| 잘못된 입력값 | 400 Bad Request |
| 인증 실패 | 401 Unauthorized |
| 접근 권한 없음 | 403 Forbidden |
| 존재하지 않는 데이터 | 404 Not Found |
| 중복 데이터 충돌 | 409 Conflict |
| 외부 비속어 검사 서비스 장애 | 503 Service Unavailable |

**선택 이유:** Controller마다 예외 처리 코드를 반복하지 않고 오류 응답을 일관되게 관리하기 위해서다.

### 2.6. 테스트 전략

JUnit과 AssertJ를 사용하여 기능별 테스트를 작성한다.

- 정상 입력에 대한 기능 동작을 검증한다.
- 상품 이름 길이, 특수문자, 비속어 검증을 테스트한다.
- 존재하지 않는 상품 조회 및 수정, 삭제 상황을 테스트한다.
- 회원가입, 로그인 및 인증 실패 상황을 테스트한다.
- 위시 리스트의 추가, 조회, 삭제 및 접근 권한을 테스트한다.
- 외부 API 검사는 테스트용 대체 구현으로 검증한다.

**선택 이유:** 기능 목록에 작성한 동작이 정상적으로 수행되는지 확인하고, 기능 변경 시 기존 동작이 유지되는지 검증하기 위해서다.

### 2.7. 코드 작성 및 커밋 전략

- 들여쓰기는 4칸으로 작성하고 최대 2단계까지만 허용한다.
- 메서드 길이는 15줄 이내로 제한한다.
- 메서드가 한 가지 역할만 수행하도록 분리한다.
- `else`, `switch`, 삼항 연산자를 사용하지 않는다.
- 기능을 구현하고 테스트한 후 기능 단위로 커밋한다.
- 커밋 메시지는 AngularJS Git Commit Message Conventions을 참고한다.

**선택 이유:** 과제의 프로그래밍 요구 사항을 준수하고, 기능별 구현 과정을 Git 기록으로 추적하기 위해서다.

## 3. AI 활용 기록

### 3.1. 활용 방법

- **사용 도구:** Claude Code (Claude)
- **과제 이해:** 과제 문서와 진행 가이드를 바탕으로 진행 순서(fork → clone → 기능 목록 작성 → 구현 → PR)를 설명받았다.
- **기능 목록 검토:** 기능 목록과 구현 전략을 작성하고, 빠진 부분이 없는지 AI에게 검토받았다.
- **구현과 테스트:** 기능 목록 한 줄 단위로 AI가 테스트와 코드를 작성하고 설명했다. 설명을 듣고 이해한 뒤 다음 기능으로 넘어갔다.
- **커밋:** 상품 등록과 상품 유효성 검사까지는 AI가 커밋했고, 상품 조회부터는 직접 커밋하고 push했다. AI는 커밋 메시지를 제안하고 올라간 결과를 확인했다.

### 3.2. 수정하거나 직접 정한 것

- AI의 설명이 길고 어려워서, 짧고 쉽게 하나씩 설명하도록 요청 방식을 바꿨다.
- 과제 문서의 필수 검증(이름 길이, 특수문자, 비속어)을 상품 등록과 수정 모두에 적용하도록 직접 짚었다.
- AI가 요청하지 않은 상태에서 README를 바꿨을 때 원래대로 되돌리게 했다.
- README의 "요구 사항 외 추가 결정" 섹션은 필요 없다고 판단해 삭제했다.
- AI가 대신하던 커밋을 직접 하는 방식으로 바꿨다.

### 3.3. 배운 점

- 처음에는 AI의 도움을 최소화하겠다는 목표로 시작했지만, 그 과정에서 어려움을 겪으며 결국 AI를 활용하였습니다. 다만 답을 얻는데 그치지 않고, AI가 답변한 것을 이해하며 기능을 설계하고 구현하는 방법을 배웠습니다. 또한 기능 단위로 작업을 나누고 커밋하는 방법을 배우면서 흐름에 조금 익숙해질 수 있었습니다.

### 3.4. 주의할 점

- AI가 작성한 코드도 설명을 듣고 이해한 뒤에 넘어가야 내 실력이 된다.
- AI가 원하지 않은 파일까지 바꿀 수 있으므로, 무엇이 바뀌었는지 직접 확인해야 한다.
