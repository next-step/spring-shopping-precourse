# spring-shopping-precourse

## 기능 요구 사항

온라인 쇼핑몰을 위한 간단한 HTTP API를 구현한다. HTTP 요청과 응답은 JSON 형식으로 주고받으며, 스프링 프레임워크를 사용하여 웹 애플리케이션으로 구현한다.

### 상품

> [기능 요구 사항](#기능-요구-사항)

상품을 조회, 추가, 수정, 삭제하는 기능을 구현한다.

#### 상품 엔티티

> [상품](#상품)

- 상품에는 이름, 가격, 이미지 URL이 포함된다.
- String name, long price, String url 로 정의한다.
- 요청 DTO의 가격은 Long으로 받는다. 가격이 빠진 요청을 null로 구분해 거절하기 위해서다.
- 엔티티의 가격은 검증을 통과한 값만 들어오므로 기본형 long으로 둔다.
- 양방향 연관관계를 가질 경우 List<Wish> wish 에 대하여 @OneToMany를 가지고 mappedBy = "product" 이다.
- 하지만 상품 -> 위시리스트는 조회할 필요 없으니 만들지 않는다.
- 상품 이미지는 파일 업로드가 아닌 URL 입력 방식으로 관리한다.
- 클래스 이름은 Product로 정의한다.
- 상품을 삭제하면 그 상품을 위시리스트에 등록한 모든 회원에 대해 해당 상품의 위시리스트를 삭제한다.
- 상품을 지우기 전에 그 상품을 가리키는 위시리스트를 먼저 지운다. 위시리스트가 남아 있으면 외래 키 제약 조건 때문에 상품을 지울 수 없다.

#### 유효성 검사 및 예외 처리

> [상품](#상품)

상품을 추가하거나 수정할 때, 클라이언트로부터 전달된 값의 유효성을 검사하고 잘못된 경우 적절한 오류 응답을 반환한다.

- 상품 이름은 공백을 포함하여 최대 15자까지 입력할 수 있다.
- 상품 이름은 반드시 입력해야 한다. 공백만 있는 이름도 입력하지 않은 것으로 본다.
- 상품 이름에는 아래 특수 문자만 사용할 수 있다.
  - 가능: `( )`, `[ ]`, `+`, `-`, `&`, `/`, `_`
  - 그 외 특수 문자는 사용할 수 없다.
  - 특수문자가 아닌 글자는 한글, 영문, 숫자, 공백만 쓸 수 있다.
- 상품 이름에는 비속어가 포함될 수 없다.
  - 비속어 검사는 길이와 특수 문자 검사를 모두 통과한 뒤에 한다. 형식이 틀린 요청으로 외부 API를 먼저 부르지 않기 위해서다.
- PurgoMalum API를 호출하여 비속어 포함 여부를 검사한다.
- 상품의 가격은 반드시 입력해야 한다.
- 상품의 가격은 0 이상, 2,147,483,647(int 최댓값) 이하만 입력할 수 있다.
- 상품 이미지 URL은 반드시 입력해야 하고, http:// 또는 https://로 시작해야 한다.

#### 상품 API

> [상품](#상품)

| URL | 메서드 | 기능 | 설명 |
|---|---|---|---|
| `/api/products` | POST | 상품 생성 | 새 상품을 등록한다. |
| `/api/products/{productId}` | GET | 상품 조회 | 특정 상품의 정보를 조회한다. |
| `/api/products/{productId}` | PUT | 상품 수정 | 기존 상품의 정보를 수정한다. |
| `/api/products/{productId}` | DELETE | 상품 삭제 | 특정 상품을 삭제한다. |
| `/api/products` | GET | 상품 목록 조회 | 모든 상품의 목록을 조회한다. |

##### 상품 생성

- 요청: `{"name": String, "price": Long, "url": String}`
- 응답: 201, `{"id": Long, "name": String, "price": Long, "url": String}`

##### 상품 조회

- 요청: 본문 없음
- 응답: 200, `{"id": Long, "name": String, "price": Long, "url": String}`

##### 상품 수정

- 요청: `{"name": String, "price": Long, "url": String}`
- 응답: 204, 본문 없음

##### 상품 삭제

- 요청: 본문 없음
- 응답: 204, 본문 없음

##### 상품 목록 조회

- 요청: 본문 없음
- 응답: 200, `[{"id": Long, "name": String, "price": Long, "url": String}]`

### 회원

> [기능 요구 사항](#기능-요구-사항)

회원 가입과 로그인을 통해 사용자 인증 기능을 구현한다.

#### 회원 엔티티

> [회원](#회원)

- 회원은 이메일과 비밀번호, 이름으로 가입할 수 있다.
- email에는 UNIQUE 제약을 걸어 같은 이메일로 두 번 가입할 수 없도록 한다.
- 이메일은 대소문자를 구분하지 않는다. 가입할 때 소문자로 바꿔 저장하고, 로그인 할 때도 소문자로 바꿔 비교한다.
- 이메일은 @ 앞뒤에 글자가 있고, @ 뒤에 점(.)이 있어야한다.
- String email과 String passwordHash, String name으로 정의한다.
- 양방향 연관관계를 가질 경우 List<Wish> wish 와는 @OneToMany관계이고 mappedBy는 "member" 이다.
- 하지만 회원 -> 위시리스트는 조회할 필요 없으니 만들지 않는다.
- 회원 클래스의 이름은 Member로 정의한다.
- 회원과 상품은 N:M 관계이다.

#### 로그인

> [회원](#회원)

- 로그인 시 이메일과 비밀번호를 검증하고, 일치하면 인증 토큰을 발급한다.
- 토큰 생성 방식은 자유롭게 선택한다.
- 이메일이 없거나 비밀번호가 틀리면, 어느 쪽이 틀렸는지 구분하지 않고 같은 메시지로 401을 반환한다.
- 어느 쪽이 틀렸는지 알려주면, 그 이메일이 가입되어 있는지를 바깥에서 알아낼 수 있다.
- 단, 회원 가입은 이미 가입된 이메일에 409를 주므로 가입 여부가 드러난다. 가입 성공 응답이 토큰이라 이미 가입된 이메일에는 같은 응답을 줄 수 없기 때문에 이것은 받아들인다.

#### 비밀번호 저장

> [회원](#회원)

- 비밀번호는 spring-security-crypto의 PasswordEncoder(BCrypt)로 해시해 passwordHash에 저장한다.
- 비밀번호 원문을 저장하지 않는다. DB가 유출되어도 원문이 드러나지 않게 하기 위해서다.
- 로그인은 matches로 맞는지 확인만 하면 되므로, 서버가 원문을 다시 꺼낼 일이 없다.
- 필드 이름을 password가 아닌 passwordHash로 지어, 원문이 아니라 해시가 들어 있다는 것을 드러낸다.
- 의존성은 spring-boot-starter-security가 아니라 spring-security-crypto만 추가한다.
- spring-boot-starter-security를 추가하면 보안 필터가 켜져, 따로 설정하기 전까지 모든 요청이 401로 막힌다.
- SecurityFilterChain으로 경로별 permitAll 설정과 세션, csrf, 폼 로그인 끄기 등 설정 부분이 많지만 과제에서 인증을 요구하는 곳이 적기 때문에 당장 구현하지않는다.
- 로그인 시 PasswordEncoder.matches로 입력한 비밀번호와 저장된 해시를 비교한다.

#### 로그인 토큰 (JWT)

> [회원](#회원)

- 토큰은 세션이 아니라 JWT를 사용한다. API명세에서 회원이 토큰을 받아야 하기 때문이다.
- 비밀번호는 로그인 할 때 한 번만 보내고, 이후 요청은 비밀번호 대신 토큰으로 인증한다.
- 라이브러리는 jjwt를 사용한다.
- 토큰은 HS256으로 서명하고, 비밀키는 설정 파일에서 읽는다.
- Payload의 sub 클레임에는 회원 id만 담는다.
- 이메일, 비밀번호 같은 정보는 넣지 않는다. Payload는 Base64URL 인코딩일 뿐이라 누구나 읽을 수 있기 때문이다.
- Payload의 iat 클레임에 발급 시각을, exp 클레임에 만료 시각을 담는다.
- 토큰은 발급 후 30분 뒤 만료된다.
- 회원 가입과 로그인에 성공하면 응답 본문으로 토큰을 반환한다.
- 응답 본문은 {"token": "발급한 JWT"} 형식이다.

##### 비밀 키

> [회원](#회원) › [로그인 토큰 (JWT)](#로그인-토큰-jwt)

- 비밀 키는 32바이트(256비트) 이상으로 정한다. jjwt는 HS256 비밀키가 이보다 짧으면 오류를 낸다.
- 실행용 비밀 키는 Github에 올리지 않고 환경 변수에 둔다. 테스트용 비밀 키는 src/test/resources/application.properties에 두고 Github에 올린다.
- 비밀 키가 새면 누구든 아무 회원 id로 올바른 서명을 만들 수 있다.
- 비밀 키는 토큰의 서명을 만들 때와 검증할 때만 쓴다. Header와 Payload를 만들 때는 쓰지않는다.
- 비밀 키는 비밀번호 해시와 관계가 없어서, 비밀 키가 새도 비밀번호 원문을 알 수 없다.

##### 요청 인증

> [회원](#회원) › [로그인 토큰 (JWT)](#로그인-토큰-jwt)

- 인증이 필요한 요청은 Authorization: Bearer {토큰} 헤더로 토큰을 보낸다. Bearer는 '소지자' 라는 의미를 가진다.
- 인증은 위시 리스트 API(/api/wishes/**)에서만 요구한다. 회원 API와 상품 API는 토큰 없이 호출 할 수 있다. 회원이 아니라도 누구나 접근할 수 있어야 하기 때문이다.
- 상품 생성·수정·삭제도 토큰 없이 호출할 수 있다. 과제 요구 사항에 권한 부분이 없어 당장 넣지 않았고, 실제 서비스라면 관리자만 호출할 수 있어야 한다. 상품을 삭제하면 그 상품을 담은 다른 회원의 위시도 함께 삭제되기 때문이다.
- 아래 경우에는 401 Unauthorized를 반환한다.
    - Authorization 헤더가 없거나 Bearer로 시작하지 않는 경우
    - 토큰 형식이 JWT가 아닌 경우
    - 서명이 일치하지 않는 경우(내용이 바뀌었거나 다른 비밀키로 만든 토큰)
    - 만료 시각(exp)이 지난 경우

### 위시 리스트

> [기능 요구 사항](#기능-요구-사항)

인증된 사용자를 대상으로 위시 리스트 기능을 구현한다.

#### 위시 리스트 기능

> [위시 리스트](#위시-리스트)

- 위시 리스트에 등록된 상품 목록을 조회할 수 있다.
- 위시 리스트에 상품을 추가할 수 있다.
- 위시 리스트에서 상품을 삭제할 수 있다.

#### 위시 엔티티

> [위시 리스트](#위시-리스트)

- 회원은 여러개의 위시(Wish)를 가질 수 있고, 상품은 여러개의 위시 리스트에 등록될 수 있다.
- 회원과 위시리스트는 1:N 관계이고 상품과 위시리스트는 1:N관계이다.
- 위시 리스트 클래스 이름은 Wish로 정의한다.
- Product product 와는 @ManyToOne 관계이고, @JoinColumn은 "product_id" 이다.
- Member member 와는 @ManyToOne 관계이고, @JoinColumn은 "member_id" 이다.
- 연관관계의 주인은 위시리스트 이다.
- FK로 member_id 와 product_id를 두고, UNIQUE제약에 (member_id, product_id)를 걸어 회원이 상품에 대한 중복된 위시 리스트를 담을 수 없도록 한다.
- 상품을 삭제하면 그 상품이 담긴 위시도 함께 삭제한다. product_id 외래키에 ON DELETE CASCADE를 건다.
- 토큰의 회원이 DB에 없으면 401 INVALID_TOKEN을 반환한다.

#### 위시 리스트 API

> [위시 리스트](#위시-리스트)

| URL | 메서드 | 기능 | 설명 |
|---|---|---|---|
| `/api/wishes` | POST | 위시 리스트 상품 추가 | 회원의 위시 리스트에 상품을 추가한다. |
| `/api/wishes/{wishId}` | DELETE | 위시 리스트 상품 삭제 | 회원의 위시 리스트에서 상품을 삭제한다. |
| `/api/wishes` | GET | 위시 리스트 상품 조회 | 회원의 위시 리스트에 있는 상품을 조회한다. |

- 위시 리스트 API는 모두 헤더에 `Authorization: Bearer {토큰}`을 담아야 한다.

##### 위시 리스트 상품 추가

- 요청: `{"productId": Long}`
- 응답: 201, `{"id": Long, "product": {"id": Long, "name": String, "price": Long, "url": String}}`

##### 위시 리스트 상품 삭제

- 요청: 본문 없음
- 응답: 204, 본문 없음

##### 위시 리스트 상품 조회

- 요청: 본문 없음
- 응답: 200, `[{"id": Long, "product": {"id": Long, "name": String, "price": Long, "url": String}}]`

#### 오류 응답

> [공통 정의 사항](#공통-정의-사항)

- 오류 응답은 Spring의 ProblemDetail (RFC 9457 표준 형식)로 반환한다.
- 상태 코드와 별개로, 원인을 구분하는 오류 코드를 확장 필드 code에 담는다. 예: "code": "PRODUCT_NAME_TOO_LONG"
- 오류코드, 상태코드, 기본 메시지는 ErrorCode enum 한 곳에 묶어 관리한다.
- Spring이 직접 내는 오류(잘못된 JSON, 검증 실패 등) 에도 code가 담기도록, ResponseEntityExceptionHandler를 상속해 handleExceptionInternal에서 code를 채운다.
- 입력 검증에 실패하면 code는 INVALID_INPUT으로 두고, 어긴 규칙을 모두 errors배열에 {field, code, message}로 담는다. 한 필드가 여러 규칙을 어기면 모두 담는다. 

##### 오류 코드 목록

## 개념 정리

### 솔트

> [회원](#회원) › [비밀번호 저장](#비밀번호-저장)

- 솔트는 비밀번호를 해시하기 전에 함께 섞는 무작위 값이고 BCrypt 해시 문자열에 그대로 드러난다.
- 솔트는 회원마다 다르고 숨기지 않는 값이며, 서버에 하나뿐이고 숨겨야 하는 JWT 비밀 키와는 다른 것이다.
- 솔트 덕분에 같은 비밀번호라도 회원마다 해시가 다르게 나온다. 해시만 보고 같은 비밀번호를 쓰는 회원을 찾을 수 없다.
- 미리 계산해 둔 "비밀번호 -> 해시" 표로 찾을 수 없어서, 공격자는 회원 한 명씩 그 회원의 솔트로 따로 대입해야 한다.

### JWT 구조

> [회원](#회원) › [로그인 토큰 (JWT)](#로그인-토큰-jwt)

- Header에는 토큰 종류와 서명 방식을 적는다.
- Payload는 전달할 정보를 담는다. payload 안의 항목 하나하나를 클레임(claim) 이라고 부른다.
- Signature를 통해 HS256(Base64URL(Header) + "." + Base64URL(Payload), 비밀키)로 계산한다. 앞 두 부분이 바뀌지 않았다는 걸 보증한다.
- 세 부분은 각각 Base64URL로 바꾼뒤 점(.)으로 이어 붙인다. Base64URL은 바이트를 HTTP헤더에 안전하게 실을 수 있는 글자로 바꾸는 인코딩이다.
- 인코딩은 누구나 되돌릴 수 있어서 Header와 Payload는 암호화되지 않는다. 내용을 숨기는 것이 아니라, 서명으로 바뀌지 않았음을 보증한다.

### 클레임

> [로그인 토큰 (JWT)](#로그인-토큰-jwt) › [JWT 구조](#jwt-구조) › Payload

- 클레임은 Payload에 담는 "이름: 값" 한 쌍이다. ex) "sub" : "3"
- 이름이 미리 정해진 표준 클레임이 있고, 이름은 3글자로 줄여 쓴다.
- 표준이 아닌 클레임(ex: "role": "USER")도 직접 추가할 수 있다.
- 시각을 나타내는 클레임은 1970년 1월 1일부터 센 초 단위 숫자로 적는다.
- 이미 이름이 정해진 클레임은 아래와 같다.

  | 클레임 | 원래 이름 | 뜻 |
  |---|---|---|
  | `sub` | subject | 토큰의 주인 |
  | `iat` | issued at | 발급 시각 |
  | `exp` | expiration | 만료 시각 |
  | `iss` | issuer | 발급한 서버 |
  | `aud` | audience | 토큰을 받을 대상 |
  | `nbf` | not before | 이 시각 전에는 무효 |
  | `jti` | JWT ID | 토큰 고유 번호 |

### HS256

> [로그인 토큰 (JWT)](#로그인-토큰-jwt) › [JWT 구조](#jwt-구조) › Signature

- HS256은 JWT 서명을 만드는 데 사용된다.
- HMAC 방식으로 SHA-256에 서버 비밀키를 섞는다.
- HS256은 서명할 때와 검증할 때 같은 비밀 키를 쓴다(대칭 키 방식). 
- RS256은 개인 키로 서명하고 공개 키로 검증한다. 여러 서버가 토큰을 검증해야 할 때 비밀 키를 나눠 주지 않으려고 쓴다.

### SHA-256

> [JWT 구조](#jwt-구조) › [HS256](#hs256)

- 어떤 입력이든 넣으면 항상 256비트(32바이트) 결과를 내는 해시이다.
- 입력이 한 글자만 바뀌더라도 결과가 완전히 달라지고 결과로 입력을 되돌릴 수 없다.
- BCrypt와 달리 매우 빠르고 솔트도 없어서 비밀번호 저장용으로 쓰지않고 데이터의 변화 유무 체크에 쓰인다.

### HMAC

> [JWT 구조](#jwt-구조) › [HS256](#hs256)

- SHA-256을 쓰면 누구나 Header.payload의 해시 값을 계산할 수 있다.
- HMAC는 계산할 때 비밀 키를 함께 넣어서 키를 아는 사람만 같은 결과를 만들 수 있게 한다.
- 즉 HS256은 SHA-256을 쓰는 HMAC이다.

### 토큰 서명에 BCrypt 대신 HS256을 쓰는 이유

> [HS256](#hs256), [비밀번호 저장](#비밀번호-저장)

- 토큰 검증은 위시 API 요청마다 일어난다. Bcrypt는 일부러 느리게 만든 것이라 요청마다 쓰기엔 너무 느리다.
- HS256은 빠르면서 키가 없으면 위조할 수 없어서 서명 용도에 알맞다.
